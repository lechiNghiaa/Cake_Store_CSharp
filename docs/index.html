Introduction

Nội dung tiệm bánh được sắp xếp theo cấu trúc tài liệu mẫu. Các mục chưa có nội dung giữ ký hiệu TODO. Tên nhóm Microservices được giữ theo mẫu; kiến trúc tiệm bánh hiện được đề xuất là một API dùng chung, chưa phải các microservice độc lập.

Bakery Website #

Tiệm bánh cần giới thiệu các loại bánh đang bán, tiếp nhận đơn từ khách hàng và phối hợp nhân viên giao hàng. Nếu thông tin sản phẩm, số lượng tồn, trạng thái đơn và tiền thu hộ được theo dõi rời rạc, nhân viên dễ xác nhận thiếu hàng, khách khó biết đơn đang ở bước nào và việc đối soát COD mất thời gian.
Đề tài phân tích và thiết kế một hệ thống trực tuyến để khách hàng xem bánh, tạo đơn và theo dõi đơn; nhân viên xác nhận, chuẩn bị và phân công giao; người giao hàng cập nhật kết quả giao; Admin quản lý danh mục bánh, tài khoản, báo cáo và duyệt đối soát COD. Các thao tác được phân theo vai trò và dự kiến ghi nhận trên cùng nguồn dữ liệu.
Hệ thống chỉ quản lý bánh đã làm sẵn. Tồn kho biểu diễn số bánh thành phẩm thực có, số lượng đang giữ cho đơn và số lượng khả dụng. Đề tài không quản lý nguyên liệu, công thức, định lượng, quy trình sản xuất hoặc đơn bánh đặt làm riêng.
Phương thức thanh toán duy nhất là COD. Người giao hàng thu tiền khi giao; hệ thống chỉ ghi nhận giao hoàn thành khi thu đủ tổng tiền COD. Khi giao thất bại, nhân viên kiểm tra tình trạng bánh hoàn về rồi quyết định giao lại hoặc kết thúc đơn theo nghiệp vụ. Hệ thống không tích hợp cổng thanh toán trực tuyến, hãng vận chuyển hay hóa đơn điện tử.
Phạm vi báo cáo dừng ở phân tích và thiết kế trong Chương 1 đến Chương 3. Các giao diện, API, cơ sở dữ liệu và môi trường chạy được trình bày như phương án đề xuất; việc xây dựng, kiểm thử và triển khai phần mềm thuộc giai đoạn tiếp theo. Để phù hợp cấu hình máy của nhóm, phương án môi trường phát triển không yêu cầu Docker.
1.2 Lý do chọn đề tài
Bán bánh có quy trình ngắn nhưng các bước phụ thuộc lẫn nhau. Số bánh khả dụng phải được kiểm tra khi khách đặt, số lượng cần giữ trong lúc chờ xác nhận và số lượng bán thực tế phải cập nhật sau khi giao thành công. Vì vậy, đề tài phù hợp để thực hành phân tích nghiệp vụ, thiết kế Use Case, mô hình dữ liệu quan hệ và giao diện đa nền tảng trong một phạm vi vừa sức.
1.3 Mục tiêu
Phân tích yêu cầu và quy trình mua bánh trực tuyến, từ lúc khách hàng đặt đơn đến khi giao hàng và đối soát COD.
Đặc tả chức năng theo 15 Use Case, vai trò người dùng và các tiêu chí chấp nhận của User Story.
Đề xuất giao diện Web cho Khách hàng, Nhân viên và Người giao hàng; đề xuất ứng dụng WinForms cho Admin.
Thiết kế mô hình dữ liệu mức ý niệm, luận lý và vật lý phù hợp với nghiệp vụ bánh thành phẩm và thanh toán COD.
Đề xuất cấu trúc phần mềm tách Web, API, Application, Domain, Infrastructure và Admin để thuận tiện cho giai đoạn xây dựng sau này.

Technical stack #

2.1 Tiêu chí lựa chọn
Nhóm lựa chọn công nghệ phù hợp với tiêu chuẩn hiện đại, dễ kiểm soát và bảo trì, có thể phát triển trên máy cá nhân, hỗ trợ giao diện Web cho người dùng và WinForms cho Admin. Cơ sở dữ liệu cần lưu dữ liệu quan hệ như đơn hàng, chi tiết bánh, trạng thái giao và khoản COD. Phương án môi trường phát triển ưu tiên cấu hình cục bộ, không bắt buộc Docker.
2.2 Công nghệ Web
Giao diện Web sử dụng HTML, CSS và JavaScript; ASP.NET Core trên .NET 9 có thể phục vụ các tệp giao diện. Khi triển khai nghiệp vụ, Web dự kiến gọi API qua HTTP để nhận dữ liệu và cập nhật trang. Phần giao diện và phần xử lý nghiệp vụ được tách riêng để dễ thay đổi, bảo trì.
CSS riêng dùng để bố trí thành phần giao diện theo kích thước màn hình và thể hiện nhận diện tiệm bánh. HTML, CSS và JavaScript tách nội dung, trình bày và thao tác của giao diện để nhóm dễ đọc và chỉnh sửa.
2.3 ASP.NET Core Web API
API được đề xuất phát triển bằng ASP.NET Core trên .NET 9. Controller tiếp nhận request, kiểm tra xác thực và chuyển yêu cầu đến dịch vụ nghiệp vụ ở Application. Infrastructure đảm nhiệm truy cập SQL Server bằng Entity Framework Core. Web và WinForms cùng gọi API để thống nhất cách kiểm tra tồn kho, chuyển trạng thái đơn và phân quyền.
Phương án xác thực dùng JSON Web Token (JWT) để API nhận diện tài khoản và vai trò. CORS giới hạn nguồn Web được phép gọi API; giới hạn tần suất có thể áp dụng cho đăng nhập và đăng ký. API trả lỗi nghiệp vụ theo cấu trúc thống nhất để giao diện hiển thị thông báo phù hợp.
2.4 WinForms cho ứng dụng Admin
Ứng dụng Admin được đề xuất phát triển bằng Windows Forms trên .NET 9 cho Windows. Krypton Toolkit có thể hỗ trợ các thành phần giao diện như Form và Button. WinForms gọi API bằng HttpClient thay vì truy cập trực tiếp cơ sở dữ liệu, để dùng chung quy tắc nghiệp vụ và cơ chế phân quyền của hệ thống.
2.5 Cơ sở dữ liệu và truy cập dữ liệu
Phương án cơ sở dữ liệu là Microsoft SQL Server, phù hợp với dữ liệu quan hệ gồm tài khoản, bánh, tồn kho, đơn hàng và đối soát COD. Entity Framework Core 9 được đề xuất làm công cụ ánh xạ đối tượng sang bảng; lớp Infrastructure sẽ đảm nhiệm truy vấn và lưu dữ liệu, còn Application gọi các thao tác theo nghiệp vụ.
Nếu nhóm lựa chọn MySQL ở giai đoạn xây dựng, cần thay đổi provider, cấu hình kết nối và kiểm tra lại kiểu dữ liệu cùng các ràng buộc. Trong thiết kế này, các bảng và kiểu vật lý được trình bày theo phương án SQL Server.

2.7 Môi trường chạy dự kiến
Trong môi trường phát triển, SQL Server có thể chạy cục bộ; API đọc chuỗi kết nối và khóa JWT từ cấu hình hoặc biến môi trường. Web và WinForms nhận địa chỉ API từ cấu hình. Phương án này không yêu cầu Docker và phù hợp để nhóm thiết lập môi trường phát triển trên máy cá nhân.
